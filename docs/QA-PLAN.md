# عاين AD Studio — خطة اختبارات الجودة الآمنة

> هذه الوثيقة خطة فقط. لا تغيّر سلوك الموقع أو إعدادات Firebase، ولا تنفّذ أي اختبار على بيانات الإنتاج.

## حدود العمل

- الفرع المستهدف: `maintenance/zero-cost-safety-2026-11-02` فقط.
- فرع `main` وموقع GitHub Pages يظلان دون تعديل في هذه المرحلة.
- لا تُستخدم حسابات Google حقيقية أو بيانات معلنين/فنانين حقيقية في الاختبارات الآلية.
- لا تُجرى عمليات إنشاء أو حذف أو تعديل على Firestore الإنتاجي.
- لا تُغيّر قواعد Firestore أو إعدادات Auth أو مفاتيح Firebase.
- لا تُضف اعتماديات أو تغيّر ملفات التطبيق قبل مراجعة أثر التغيير والموافقة عليه.
- الميزانية المستهدفة: صفر دولار؛ يجب مراجعة حصص GitHub Actions وأي تنزيلات متصفحات قبل اعتماد تشغيل متكرر.

## الوضع المعروف حالياً

- اختبارات Firestore Rules موجودة في `tests/firestore.rules.test.mjs`.
- إعداد Firebase Emulator الحالي يعرّف Firestore Emulator فقط؛ لا يظهر Auth Emulator في `firebase.json`.
- لا يوجد إعداد موثق لاختبارات متصفح End-to-End في الإعدادات التي تمت مراجعتها.
- نجاح اختبارات قواعد Firestore لا يثبت نجاح Google Sign-In أو رحلة المستخدم كاملة.

## المرحلة 1 — جرد قبل التنفيذ

1. فحص جميع ملفات `package.json` وملفات القفل وإعدادات CI بحثاً عن Playwright أو Cypress أو Puppeteer.
2. التأكد من إصدارات Firebase CLI وFirebase JS SDK المستخدمة، وتوافق Auth Emulator معها.
3. تحديد نقطة تشغيل الموقع في بيئة اختبار محلية، مع منع أي اتصال بمشروع Firebase الإنتاجي.
4. مراجعة ما إذا كانت ملفات `tests/` تُنشر كمسارات عامة عبر GitHub Pages قبل إضافة أي ملفات إليها.
5. توثيق المتطلبات والوقت المتوقع وحجم تنزيل المتصفح، والتأكد من ملاءمتها للحصة المجانية.

## المرحلة 2 — بيئة معزولة

- تشغيل Firestore Emulator وAuth Emulator محلياً أو داخل GitHub Actions فقط.
- استخدام مشروع Firebase تجريبي مخصص للاختبار، وعدم وضع أسرار إنتاجية في المستودع.
- إعداد بيانات اختبار اصطناعية قابلة لإعادة التهيئة.
- جعل الاختبارات تفشل بوضوح إذا تعذر الاتصال بالمحاكيات، بدلاً من الرجوع إلى Firebase الإنتاجي.
- لا يبدأ تنفيذ هذه المرحلة قبل مراجعة التغييرات المقترحة على ملفات الإعداد والاعتماديات.

## المرحلة 3 — سيناريوهات المتصفح ذات الأولوية

| حرجة | تسجيل الدخول التجريبي | تظهر حالة المستخدم الصحيحة بعد اكتمال Auth Emulator |

| حرجة | تحديث الصفحة بعد تسجيل الدخول | تستعاد حالة الجلسة التجريبية دون مطالبة متكررة بالتسجيل |

## المرحلة 4 — معايير القبول

- كل اختبار يوضح بجلاء أنه يعمل على المحاكيات لا الإنتاج.
- لا تُسجل رموز دخول أو كلمات مرور أو بيانات شخصية في السجلات.
- الاختبارات الحالية التسعة لقواعد Firestore تظل ناجحة دون تغيير معناها.
- لا يتغير أي ملف من ملفات واجهة الموقع أو لوحة الإدارة ضمن إعداد الاختبارات وحده.
- لا دمج إلى `main` ولا نشر قبل مراجعة النتائج وموافقة صاحب المشروع.

## قرار التنفيذ التالي

الخطوة التالية المسموح بها هي إكمال جرد الاعتماديات وسير العمل، ثم تقديم قائمة دقيقة بالملفات التي قد تتأثر وأسباب كل تعديل. لا تُعدّل `package.json` أو `firebase.json` أو Workflow ولا تضف Playwright/Auth Emulator قبل هذه المراجعة.


## نتائج الجرد التفصيلي — 2026-11-02

### ما تم التحقق منه

- `package.json` يحتوي فقط على اختبار `test:rules`، ويشغّل Firebase Emulator مع Firestore فقط.
- لا يوجد `package-lock.json` أو `npm-shrinkwrap.json` في جذر الفرع؛ لذلك تثبيت CI الحالي عبر `npm install` لا يعتمد على lockfile محفوظ في المستودع.
- `firebase.json` لا يعرّف Auth Emulator.
- Workflow الحالي يثبت Node 20 وJava 21، ثم ينفذ `npm install` و`npm test`. لا توجد خطوة تثبيت أو تشغيل Playwright/Cypress/Puppeteer في هذا الـ workflow.
- مجلد `tests/` يحتوي ملفات HTML إضافية ونسخة قواعد Firestore أقدم مختلفة عن ملف الجذر. لا يجوز حذفها أو نقلها قبل التحقق من استخدامها ومسارات النشر.
- ملف `tests/index.html` مختلف عن `index.html` الأساسي؛ لذا لا يُفترض أنه نسخة مطابقة أو بيئة اختبار آمنة.
- تطبيق الموقع يستخدم Firebase JS SDK من CDN ويهيئ Auth وFirestore مباشرة في صفحة التطبيق. لا يظهر في موضع التهيئة الذي تمت مراجعته أي ربط بمحاكيات Auth أو Firestore.
- لا توجد حتى الآن آلية مثبتة تمنع نسخة المتصفح التجريبية من الاتصال بمشروع Firebase الحقيقي؛ لذلك لا يجوز تشغيل اختبارات واجهة آلية على الصفحة الحالية قبل تصميم حاجز صريح يمنع الاتصال بالإنتاج.

### مخاطر يجب عدم تجاوزها

1. عدم وجود lockfile يجعل نسخ الاعتماديات غير ثابتة بين مرات التثبيت؛ أي إضافة اختبار متصفح قبل معالجة هذا الأمر قد تزيد عدم قابلية إعادة الإنتاج.
2. لا يمكن اختبار Google OAuth الحقيقي داخل محاكي Auth باعتباره تدفق Google الإنتاجي نفسه؛ يجب فصل اختبار حالة الجلسة وسلوك التطبيق عن اختبار OAuth الفعلي، وعدم استخدام حسابات حقيقية في CI.
3. توصيل التطبيق بالمحاكيات يتطلب نقطة تهيئة اختبارية معزولة. لا نضيف شرطاً عاماً في التطبيق قد يوجّه زوار الموقع إلى المحاكيات أو يغيّر سلوك الإنتاج.
4. وجود ملفات داخل `tests/` لا يثبت أنها غير منشورة؛ يجب فحص إعداد GitHub Pages ومسارات النشر قبل اعتبارها ملفات داخلية.

### التوصية الفنية قبل أي اعتماديات جديدة

- أولاً: حصر إعداد النشر الفعلي ومصدر GitHub Pages.
- ثانياً: إعداد مدخل اختبار منفصل لا يُستخدم في الموقع العام، ويشترط عنواناً محلياً/بيئة CI معروفة قبل السماح بالاتصال بالمحاكيات.
- ثالثاً: تثبيت الاعتماديات بصورة قابلة لإعادة الإنتاج بعد تحديد إصدارات متوافقة، ثم تقييم تكلفة Playwright وحجم تنزيل Chromium على GitHub Actions.
- رابعاً: فصل سيناريوهات Auth Emulator (جلسة مستخدم اختبارية) عن Google OAuth الحقيقي، مع اختبار OAuth اليدوي خارج CI عند الحاجة.
- خامساً: إضافة الاختبارات على فرع الصيانة فقط وتشغيلها ضد المحاكيات، ثم مراجعة النتائج قبل أي دمج.

**الحالة:** لم يتم تعديل كود التطبيق أو قواعد Firestore أو إعدادات Firebase أو Workflow أو الاعتماديات. هذه النتائج توثيقية فقط.


## مراجعة مسارات النشر وملفات الاختبار — 2026-11-02

### نتائج مؤكدة من المستودع

- المستودع عام (Public)، والفرع الافتراضي هو `main`.
- الـWorkflow الوحيد الذي تمت مراجعته هو `.github/workflows/firestore-rules.yml`.
- الـWorkflow يعمل عند `pull_request` إذا تغيّرت ملفات القواعد أو `tests/**` أو ملفات إعداد محددة، ويعمل عند `push` إلى `main`. لا يوجد trigger خاص بالدفع إلى فرع الصيانة.
- لذلك لن نحصل على فحص آلي بمجرد commit على فرع الصيانة؛ يلزم لاحقاً Pull Request كي يعمل فحص المسارات، لكن لا يتم الدمج تلقائياً.
- `tests/index.html` صفحة HTML كاملة مختلفة عن `index.html` الجذر، لكنها تستخدم إعداد Firebase الخاص بالمشروع الحقيقي `ayn-marketplace` وتستورد Firebase JS SDK من CDN. لذلك لا تصلح كمدخل اختبار معزول، ولا ينبغي تشغيل اختبارات تفاعلية عليها باعتبارها بيئة تجريبية.
- `tests/ayin-panel-k7x2.html` مطابقة بايتياً لملف لوحة الإدارة في الجذر بحسب SHA نفسه؛ لا تُحذف أو تُنقل دون معرفة سبب وجودها.
- `tests/firestore.rules` مختلفة عن `firestore.rules` في الجذر وأقدم منها بحسب SHA والمقارنة السابقة؛ لا ينبغي أن تُستعمل كقواعد إنتاج أو استبدال القواعد الأساسية.
- يوجد ملف صغير باسم `tests/.exmu-cfg1.data` بمحتوى opaque غير موثق. لم نكشف محتواه في التقرير ولم نعدّله؛ يجب تحديد منشئه ومراجعته قبل حذفه أو نقله.

### ما لم نتمكن من إثباته بعد

- إعداد مصدر GitHub Pages (branch/folder أو custom workflow) غير ظاهر ضمن صلاحيات قراءة ملفات المستودع التي استخدمناها؛ لم نتمكن من قراءة إعداد Pages الإداري.
- تعذّر التحقق المباشر من فتح المسار المنشور `/tests/index.html` عبر أداة التصفح في هذه الجلسة.
- لذلك لا نجزم أن `tests/` منشور حالياً للعامة، رغم أن المستودع عام ويحتوي ملفات HTML قابلة للنشر إذا كان مصدر Pages هو جذر الفرع.

### قرار السلامة

- لا نضيف اختبارات إلى `tests/` قبل حسم ما إذا كان مجلد الاختبارات يُنشر.
- لا نعيد استخدام `tests/index.html` الحالي كبيئة اختبار؛ فهو يتصل بإعداد Firebase الإنتاجي.
- لا نعدّل ملفي HTML أو قواعد Firestore أو إعداد Pages.
- قبل تنفيذ أي بيئة E2E، نحتاج معرفة مصدر GitHub Pages من إعدادات المستودع، ثم نختار مجلداً خارج مسار النشر أو workflow منفصلاً لا يغيّر الموقع.


## تأكيد مصدر GitHub Pages من إعدادات المستودع — 2026-11-02

تم تأكيد الإعداد من لقطة شاشة أرسلها مالك المشروع من صفحة Settings → Pages:

- Source: **Deploy from a branch**.
- Branch: **main**.
- Folder: **/(root)**.
- الصفحة الحية معروضة في إعدادات GitHub Pages على الرابط الأساسي للمشروع.

### النتيجة العملية

- GitHub Pages ينشر محتويات جذر فرع `main`، بما فيها المسارات الفرعية الموجودة تحته.
- لذلك ملفات HTML الموجودة داخل `tests/` ضمن نطاق النشر المحتمل كمسارات عامة تحت الموقع، وليست مساحة خاصة أو مخفية للاختبارات.
- لا تستخدم `tests/index.html` أو أي صفحة اختبار موجودة هناك لتجارب تفاعلية؛ فقد تتصل بإعداد Firebase الحقيقي، كما أنها ضمن شجرة النشر.
- لا تنقل أو تحذف الملفات الموجودة حالياً في `tests/` ضمن هذه الخطوة؛ فقد يؤثر ذلك على روابط منشورة أو سلوك قائم.

### قرار التنفيذ المحدّث

1. لا نضع أي صفحات اختبار جديدة داخل جذر `main` أو أي مجلد فرعي منه.
2. ندرس إعداد اختبارات المتصفح داخل GitHub Actions على فرع الصيانة فقط، مع تشغيل خادم محلي داخل الـworkflow وعدم نشر ملفات الاختبار عبر Pages.
3. قبل إضافة أي إعدادات أو اعتماديات، نراجع التغيير المقترح في ملفات منفصلة ونضمن أن الاتصال بالمحاكيات فقط، مع حاجز فشل يمنع الوصول إلى مشروع Firebase الإنتاجي.
4. لا تغيير على مصدر Pages أو فرع `main`، ولا تعديل على Firebase الإنتاجي أو واجهات الموقع.

**الحالة:** مصدر Pages أصبح مؤكداً من لقطة إعدادات GitHub. لم يتم تغيير إعداد Pages أو ملفات التطبيق أو ملفات الاختبار الحالية.


## مراجعة قابلية تنفيذ اختبارات المتصفح — 2026-11-02

### ما كشفته مراجعة الملفات الحالية

- ملف التطبيق `index.html` يحمّل Firebase JS SDK 10.12.2 مباشرة من CDN، ويحتوي إعداد مشروع `ayn-marketplace` داخل الصفحة.
- تهيئة التطبيق الحالية تستعمل `initializeApp` ثم `getAuth` و`getFirestore`، ولا تستدعي `connectAuthEmulator` أو `connectFirestoreEmulator`.
- لذلك فإن تشغيل `index.html` كما هو داخل Playwright لا يجعله يستخدم المحاكيات تلقائياً؛ بل سيحاول استخدام إعداد Firebase الموجود في الصفحة.
- لا يوجد حالياً مدخل اختبار منفصل أو متغير إعدادات آمن يبدّل مشروع Firebase ونقاط اتصال المحاكيات.
- اختبارات القواعد التسعة تستعمل مشروع Emulator باسم `demo-ayn-marketplace` وتقرأ القواعد من ملف الجذر، وهذا جيد لاختبارات القواعد، لكنه لا يختبر تدفق واجهة التطبيق أو Google OAuth.
- Workflow الحالي يستخدم `npm install` ولا يوجد lockfile في الجذر؛ تثبيت الاعتماديات ليس مثبت الإصدارات بالكامل. لا نضيف Playwright أو اعتماديات جديدة قبل حسم طريقة تثبيت قابلة للتكرار والحصة المجانية.

### حدود الاختبار الآمن

**يمكن اختباره دون تعديل التطبيق:** فحوصات الملفات والبنية، واختبارات قواعد Firestore الحالية على Emulator، وفحوصات متصفح شكلية لا تشغّل وظائف Firebase ولا ترسل بيانات.

**لا يمكن ادعاء اختباره بأمان حتى الآن:** رحلة تسجيل Google الحقيقية، استعادة جلسة المستخدم في التطبيق، إنشاء حساب من الواجهة، وإرسال طلب إعلان من الواجهة. السبب أن نقطة تهيئة Firebase في التطبيق مرتبطة بإعداد المشروع الحقيقي ولا يوجد حاجز Emulator داخل التطبيق.

### تصميم التنفيذ المقترح — لم يُنفّذ

1. الإبقاء على اختبارات Firestore الحالية كما هي، وعدم تغيير قواعدها أو نتائجها.
2. بناء نسخة اختبار مؤقتة داخل مساحة العمل في GitHub Actions فقط، لا تُرفع إلى GitHub Pages ولا تُحفظ كصفحة HTML جديدة داخل جذر المستودع.
3. وضع حاجز صريح في بيئة الاختبار: project ID تجريبي يبدأ بـ `demo-`، وعناوين Auth/Firestore Emulator محلية فقط؛ وإيقاف الاختبار فوراً إذا ظهر `ayn-marketplace` أو أي عنوان إنتاج.
4. فصل اختبار العرض/التفاعل الشكلي عن اختبار Firebase. لا تُستخدم حسابات Google حقيقية في CI، ولا يُعتبر Auth Emulator اختباراً لـ Google OAuth الإنتاجي.
5. قبل اختيار Playwright أو أي أداة، التحقق من حجم تنزيل المتصفح، زمن التشغيل، حدود GitHub Actions المجانية، وإمكانية تثبيت الاعتماديات دون تحديثات غير مقصودة.
6. لا نعدّل `index.html` أو `package.json` أو `firebase.json` أو Workflow قبل عرض التغيير المحدد ومراجعته؛ وإذا احتاج الاختبار إلى نقطة تهيئة جديدة في التطبيق، نطلب موافقة منفصلة بعد شرح أثرها.
7. عند التنفيذ، تُحفظ أدوات الاختبار في مسار غير منشور أو تُنشأ وقت التشغيل داخل مجلد مؤقت في CI، ولا تُنشر إلى Pages.

### قائمة الملفات المحتمل أن تتأثر لاحقاً

| الملف/المسار | سبب احتمالية التغيير | القرار الآن |

| `.github/workflows/...` | تشغيل خطوات اختبار المتصفح في CI | لا تغيير |

| مسار أدوات QA مخفي/مؤقت | ملفات الاختبار والتهيئة غير المنشورة | لا إنشاء الآن |

**قرار المراجعة:** لا توجد حالياً طريقة آمنة ومباشرة لتشغيل اختبارات E2E على صفحة التطبيق الحالية دون بناء حاجز اتصال معزول. لذلك توقّف التنفيذ عند مرحلة التصميم والمراجعة؛ لم تُضف أداة أو اعتماديات، ولم تُشغّل أي متصفح ضد الموقع أو Firebase.
